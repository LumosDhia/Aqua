# AquaFarm device integration diagnosis

## Summary

Use Aqua’s existing server-side board bridge on an always-on farm host joined to the AquaFarm access point.  
The current firmware already supplies live sensors, pump state, mode and alarms to that bridge, which writes linked-plot readings.  
Bench-test the unchanged board first with the pump disconnected. Fix the reversed mode gate, the 3-second validation failure and stop confirmation before enabling remote pump control.  
Keep the board responsible for watering decisions, dry-run protection and pump timing.  
This is a source-code diagnosis. The deployed firmware, network and pump were unavailable for verification.

All routes below are under `/api`. The browser calls Aqua via `API_BASE` (same origin by default) and adds `Authorization: Bearer <user JWT>`. ### Existing local board bridge and history

- FastAPI starts `backend/app/bridge.py` in its lifespan. Each pass sequentially polls `GET /data` for every stored local URL with a 4 s HTTP timeout, then waits 5 s. Network failures skip that board and leave its previous snapshot and `last_seen`. The base URL is private numeric plain HTTP with optional port and no non-root path, query or user credentials. There is no board key, reachability probe at add time or mDNS/scan. `discovery.py` is job discovery, with only `GET /api/opportunities` and `GET /api/farms/{farm_id}/candidates`. Evidence `backend/app/main.py:41–51`, `backend/app/main.py:65–70`, `backend/app/bridge.py:21–55`, `backend/app/bridge.py:97–120`, `backend/app/routers/devices.py:237–245`, `backend/app/routers/discovery.py:31–35`, `backend/app/routers/discovery.py:66–70`.
- Ingest keeps the entire board JSON, normalizes `rain,pump,alarm,auto` to booleans, populates device status/mode/alarm and creates or updates `pump1`. The current bridge guesses 30 s for an observed run without a deadline. ## 5. Recommended architecture and wire contract

```text
 Farmer's browser
   |  Aqua web + /api, same origin, user Bearer token on API
   |  farm LAN, or private VPN to that origin for remote access
   v
 Always-on farm host -- native FastAPI + built web, one bridge worker
   |  LAN/Ethernet: browser and canonical farm database traffic
   |  Wi-Fi: joins the isolated AquaFarm AP, route to 192.168.4.1
   |     GET /data
   |     POST /pump?action=on&sec=5    or    POST /pump?action=off
   |     POST /mode?auto=0            or    POST /mode?auto=1
   v
 Physical AquaFarm ESP32 -- sensors, Auto rules, dry-run interlock, relay timer

 FastAPI -> Device snapshot + Actuator + DeviceCommand
         -> linked-plot Reading rows -> plot history, overview and irrigation advice
```

**Provisioning and ownership.** The owner supplies the actual board SSID and AP password to the host, its actual board IP, and an authorized Aqua account. The farmer selects the existing farm and plot in Devices, uses **Board on the farm network**, and enters the board address and a display name. The local connection uses no `DEVICE_TOKEN` or new farm router credentials on the ESP32. Configure the host's LAN interface separately (prefer Ethernet), keep its default route and DNS on the LAN, give the AP interface a route for the board subnet only, and disallow routing/forwarding to the AP from LAN/VPN clients. Ensure the LAN and VPN ranges do not overlap the AP. Use a unique AP password and keep access to the board AP with the host and authorized maintenance staff. The AP password in the repository is an example in source. Restrict board destinations to the configured AP IP and port per deployment. Keep the board's plain HTTP on that link. Evidence for the existing setup fields and access constraints `firmware/aquafarm_standalone/aquafarm_standalone.ino:14–15`, `firmware/aquafarm_standalone/aquafarm_standalone.ino:456–467`, `backend/app/bridge.py:35–55`, `web/src/components/devices/DeviceDialog.tsx:246–348`.

**Host and database.** First bench run on the host with `./run-farm.sh` in its supported Bash environment, a built `web/dist`, and `local/farm.env` pointing at a bench database with an actual farm/plot and `WEB_DIR` pointing at the built web directory. Open `http://127.0.0.1:8800` on that host. For continuous farm operation, run the same app with a LAN-reachable listener, same-origin HTTPS for shared access, and the authoritative farm database reachable on the farm LAN. If farm data is currently in the VPS database, migrate it as a planned cutover or agree on the WAN dependency before deployment. A VPS database over the script's SSH tunnel remains a dependency if retained. Restrict the listener to the LAN/VPN via bind address or firewall. Use one API instance and one board identity on the board-facing deployment to avoid duplicate control and history. Configure request limits and allow only the approved board address in the bridge. Evidence for the launcher, static-mount requirement and in-process poller `run-farm.sh:2–19`, `backend/app/config.py:4–18`, `backend/app/main.py:41–48`, `backend/app/main.py:79–80`, `backend/app/bridge.py:27–28`, `backend/app/bridge.py:97–120`.
